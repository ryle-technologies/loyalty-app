## 1. Resumen / one-liner

**One-liner:** Sellos de fidelidad para tu café que solo tu equipo puede sumar y canjear: sin trampas ni sellos transferibles, y tus clientes ven su progreso en cada WhatsApp.

*Nota de posicionamiento:* “sin app / sin descargar nada” es **table stakes** en la categoría (Aleatix, Lea, Lealify) y no se presenta como diferenciador. Diferenciadores: control del staff, antifraude (ledger append-only, idempotencia, topes, no transferible) y progreso simple por WhatsApp.

**Qué es:** Feature SaaS B2B para comercios. El staff suma y canjea sellos desde un panel web ligero; el cliente final solo recibe notificaciones por WhatsApp (sin app). Cobro mensual solo al comercio.

**Qué no es (MVP):** App de cliente, paquetes de servicios, caducidad de sellos, WhatsApp conversacional / consulta de saldo, freemium, lifetime, transferencia P2P, cash-out, merge dual-OTP global, analytics complejos, Wallet (diferido), prepago anual (diferido).

## 2. Goals & success metrics (soft launch)

### 2.1 Objetivos de producto
1. Validar que un comercio real puede operar earn/burn en ≤3 toques entre pedidos.
2. Confirmar que el cliente entiende y usa el programa solo vía WhatsApp (sin app).
3. Demostrar ledger consistente (sin doble earn, sin burn inválido).
4. Aprender flows con leads reales en el **mercado de soft launch** (UY si hay lead real dispuesto a operar en 14 días; si no, CO), sin dependencias de país, mientras las entrevistas de WTP deciden el beachhead.

### 2.2 Métricas de éxito (soft launch)
| Métrica | Criterio mínimo |
|---------|-----------------|
| Comercios operando | ≥1 comercio real del mercado de soft launch usando el panel sin app de cliente |
| Flujo earn/burn | Completado en ≤3 toques + WhatsApp enviado |
| Invite → active | Al menos 1 cliente real confirma por WhatsApp (*SÍ*) |
| Integridad ledger | 0 dobles earn por doble-click en pruebas + operación real |
| Dashboard | Home muestra KPIs §8.4 y listas pendientes / inactivos / listos |
| Transferencia | Imposible mover sellos entre Persons (tests + invariante) |

### 2.3 Métricas internas de psicología (PMAT §5; sin pantalla nueva)
| Métrica | Para validar |
|---------|--------------|
| % memberships que completan el 1er ciclo | Endowment + N |
| Días hasta el primer burn | Goal-gradient / N |
| % que hacen el 1er earn del 2º ciclo 14–30 días tras el burn | Puente post-canje |
| Tasa de decline / *BAJA* de invitaciones | Reactancia del copy |
| (P2) Retención 60/90 con vs sin Wallet | R8 (diferido) |

A/B formales aplazados (poco volumen); comparar entre comercios o antes/después. Candidatos: 0 vs 2 welcome; hito on/off; `post_burn_bonus_stamps` 0 vs 1.

### 2.4 Fuera de métricas soft launch
- MRR automatizado, churn, LTV, NPS formal, benchmarks multi-país.

## 4. In scope / Out of scope

### 4.1 In scope (MVP)
- Auth staff (email) + roles `owner` | `staff`
- Alta Merchant (país, moneda, timezone por comercio) + 1 Program activo (N default 10, reward_label, welcome, topes diarios)
- Person + Membership + flujo atómico invitar + primer sello → confirmación *SÍ* → active + sellos de bienvenida
- Ledger append-only: earn, burn, adjust (con reason / reason_code)
- Panel: buscar, invitar(+sumar), +sello, canjear ≤3 toques
- WhatsApp outbound con plantillas aprobadas por Meta (invite, bienvenida, earn con hitos, earn+reward, burn con puente)
- Inbound técnico solo *SÍ* y *BAJA*
- Cambio de teléfono **local**: reasigna la Membership (`staff_local`) + auditoría
- Dashboard KPIs mínimo soft launch (§8.4) + 2–3 sugerencias por reglas
- Subscription: trial 14d + founding/list con precio en moneda local; billing **manual OK** en soft launch
- i18n copy ES; timezone del merchant
- Idempotencia, topes diarios, sellos no transferibles

| Ítem | Nota |
|------|------|

| Caducidad de sellos (`expires_stamps`) | Siempre `false` en MVP |
| WhatsApp conversacional / consulta de saldo | No (solo *SÍ*/*BAJA*) |
| Freemium perpetuo / lifetime / one-time | No |
| Transferencia de sellos / P2P / cash-out | Prohibido |
| Person merge dual-OTP global | Post soft launch |
| App nativa de cliente | No |
| Stripe multi-país día 1 | Manual OK en soft launch |
| Analytics complejos (LTV, cohortes, heatmaps, ML, ranking gamificado) | No |
| Export masivo de teléfonos sin rol owner | No |
| Comparador con otros cafés de la red | No |
| Más de 1 programa activo por comercio | No requerido en MVP |
| WA automático a inactivos / recordatorios entre visitas / campañas | No (reactancia + coste) |
| Email del cliente | No |
| **Apple/Google Wallet** | **Diferido / Deferred** — fase 2 (E-PSY-6, P2); el pase reflejaría `balance_cache`; el modelo no debe impedirlo |
| **Prepago anual** | **Diferido / Deferred** — tras elegir mercado de pago |

### 5.3 Gaps detectados
| Gap | Impacto | Resolución / default |
|-----|---------|------------------|
| G1 | ¿Decline / *BAJA* se puede re-invitar? | Sí: re-invite → `pending` + nuevo WA, solo por acción explícita del staff; sin outbound mientras `whatsapp_opt_in=false` salvo la nueva invitación. |
| G2 | Earn en el mismo flujo de invite | **Resuelto:** `POST /memberships/invite` con `earn_now: true` (§10.1). |
| G3 | Bootstrapping sin inbound | **Resuelto:** inbound *SÍ* es requisito; confirmación en persona queda como fallback auditado, **sin** sellos de bienvenida. |
| G4 | `reward_available` cálculo | `true` cuando `balance_cache >= stamps_required`. Tras burn, recalcular. |
| G5 | ¿Varios StaffUsers owner? | 1 owner al crear merchant; owner puede invitar más staff (`role=staff`). Segundo owner = post-MVP. |
| G6 | Password reset / magic link | Builder elige; debe existir reset seguro antes de soft launch. |

## 6. Functional requirements (FR-xxx)

### Auth & Merchant
- **FR-001** StaffUser autentica con email + credencial; sesión scoped a `merchant_id`.
- **FR-002** Roles: `owner` (config programa, adjust, billing view) y `staff` (ops diarias).
- **FR-003** Crear Merchant con `name`, `country`, `currency`, `timezone` (IANA, obligatorio, sin default de país), `status=active`.
- **FR-004** Owner crea/edita Program: `name`, `stamps_required` (N≥1, default 10), `reward_label`, `stamps_per_earn` (default 1), `welcome_stamps` (0–2, default 2), `welcome_reason` (obligatorio si `welcome_stamps>0`), `post_burn_bonus_stamps` (0–1, default 0; P1), topes diarios (defaults 2/1), `status`.
- **FR-005** Invariantes de Program: `expires_stamps=false`, `stamps_transferable=false` (no editables en UI MVP).

### Person & Membership
- **FR-010** Teléfono almacenado y validado en E.164; unique global en Person.
- **FR-011** Invite: find-or-create Person → create Membership `invite_status=pending`. Con `earn_now=true`, en la misma transacción se registra el primer `earn` (FR-016).
- **FR-012** Unique `(merchant_id, person_id)` — no duplicar membership.
- **FR-013** Confirmación *SÍ* → `invite_status=active`, `whatsapp_opt_in=true` → si `welcome_stamps>0`, evento `adjust` de sistema (FR-028) → WA bienvenida con saldo real (`actual / N`).
- **FR-014** Decline → `invite_status=declined`; no earn/burn.
- **FR-015** Buscar memberships por teléfono (parcial/E.164) o `display_name`.
- **FR-016** Invitar + primer sello atómico: Person + Membership `pending` + evento `earn` (+`stamps_per_earn`) + encolado de WA invite en una sola transacción, con `idempotency_key`; cuenta para topes y KPIs como un earn normal. Es la **única** excepción a “earn solo si active”.
- **FR-017** Confirmación en persona (fallback): `active` + bienvenida + `StaffAuditEvent`; **no** concede `welcome_stamps`.

### Ledger
- **FR-020** Earn: crea `StampLedgerEvent` tipo `earn`, `delta=+stamps_per_earn` (default +1), actualiza `balance_cache`, `reward_available`, `last_activity_at`.
- **FR-021** Burn: solo si `balance_cache >= stamps_required` y `reward_available`; `delta=-stamps_required` en transacción con lock; auditar. Si `post_burn_bonus_stamps>0` (P1): `adjust` de sistema `reason_code=post_burn_bridge` en la misma transacción.
- **FR-022** Adjust manual: `delta` ± con `reason` obligatorio; solo owner; `reason_code=manual`; auditar.
- **FR-023** Toda mutación ledger exige `idempotency_key` único por merchant (o global); replay → misma respuesta, sin segundo evento ni segundo WA.
- **FR-024** Earn/burn solo si Membership `invite_status=active` (salvo FR-016) y Program `status=active` y Merchant `status=active`.
- **FR-025** Respetar `max_earns_per_day` (default 2) / `max_burns_per_day` (default 1) por membership y día en la timezone del merchant. Los `adjust` de sistema no cuentan.
- **FR-026** Ledger append-only: no UPDATE/DELETE de eventos; saldo real = suma de deltas.
- **FR-027** Imposible transferir saldo entre Persons/Memberships.
- **FR-028** Sellos de bienvenida: `type=adjust`, `delta=+welcome_stamps`, `actor_staff_user_id=null`, `reason_code=welcome_endowment`, `reason=welcome_reason` renderizado, `idempotency_key = "welcome:" + membership_id` (máx. 1 por membership, aunque haya re-invites). Excluido de topes y de KPIs (`earns_7d`, `active_30d`, canje).

### Panel ops
- **FR-030** Flujo earn desde búsqueda → detalle → +Sumar sello en ≤3 toques.
- **FR-031** Flujo burn: ver recompensa disponible → confirmar canje ≤3 toques.
- **FR-032** Invite (+sumar) desde panel con teléfono (+ nombre opcional) ≤3 toques.
- **FR-033** Listas: pendientes, listos para canjear, inactivos 21d, búsqueda; *(P1)* casi listos.
- **FR-034** Home “Hoy”: KPIs §8.4 + CTAs Buscar / Invitar + avisos.

### WhatsApp
- **FR-040** Outbound solo con plantillas utility aprobadas por Meta: invite, bienvenida, earn (con hitos), earn+reward, burn (copy §12). Máx. 1 WA por evento ledger exitoso.
- **FR-041** Inbound *SÍ* (case-insensitive, variantes SI/Sí/si/sí): activa la Membership pending más reciente de ese teléfono (FR-013). Idempotente.
- **FR-042** Persistir `whatsapp_message_id` en ledger cuando aplique; fallos de envío no revierten el ledger (reintento/cola); UI muestra estado de notificación si falla.
- **FR-043** Inbound *BAJA* (variantes BAJA/baja/STOP): `whatsapp_opt_in=false` en las Memberships de esa Person (default: todas las del número; el mensaje no indica comercio) y se detiene todo outbound; el ledger sigue operando. Respuesta de confirmación única si la política del proveedor lo permite.
- **FR-044** Cualquier otro inbound se ignora (sin conversación ni consulta de saldo).

### Teléfono & auditoría
- **FR-050** Cambio teléfono local (`staff_local`): **nunca** se edita `Person.phone_e164`. Se busca o crea la Person del número nuevo y se reasigna **solo** esta Membership (`person_id`) a ella; el ledger conserva el histórico (los eventos nuevos llevan el nuevo `person_id`). Se registra `PersonMergeEvent` (`method=staff_local`, `merchant_id`, `membership_id`) + `StaffAuditEvent`. Si la Person del número nuevo ya tiene Membership en este comercio → **409** (colisión; ver OQ-8).
- **FR-051** Toda acción sensible (invite, earn, burn, adjust, phone change, program patch, confirm-in-person, resend) genera `StaffAuditEvent`.

### Billing
- **FR-060** Al crear el merchant: Subscription `status=trialing`, `trial_ends_at=now+14d`. Si `now < founding_window_ends_at` **y** slots reservados < 50 (global): `plan=founding`, `founding_slot=true` (reserva), `founding_ends_at = trial_ends_at + 6 meses`, precio founding en moneda local; si no, `plan=list`.
- **FR-061** Tras trial: `active` a precio founding o list según el slot. Al vencer `founding_ends_at` → `plan=list`, precio list. Si cancela antes de `first_charged_at` → `founding_slot=false` y el slot vuelve al cupo (si la ventana sigue abierta).
- **FR-062** Cobro manual permitido en soft launch; `provider_customer_id` opcional.
- **FR-063** No lifetime / one-time en UI ni API.
- **FR-064** `plan` es extensible (futuros `wallet`/`pro`, fuera del founding); el precio vive en `price_amount` + `currency`, nunca en campos por moneda.

### Analytics
- **FR-070** `GET /analytics/summary` devuelve campos §10 / §11 (incl. `almost_ready_count`, P1).
- **FR-071** Sugerencias solo con reglas fijas con señal (canje bajo, inactivos, invites pendientes); si no hay señal, no mostrar consejo inventado.
- **FR-072** Métricas internas de psicología (§2.3) calculables desde el ledger, excluyendo `welcome_endowment`.

## 7. Épicas + user stories

**Convención:** US-Exx-yy. Cada historia incluye criterios de aceptación (AC) y casos negativos donde aplica.

### E1 — Auth + Merchant + Program setup
**Objetivo:** Staff puede entrar y dejar un programa activo listo para operar.

#### US-E1-01 — Login staff
**Como** StaffUser, **quiero** iniciar sesión con email, **para** acceder al panel de mi comercio.

**AC:**
- Given credenciales válidas, When login, Then sesión autenticada scoped a `merchant_id` y rol.
- Given credenciales inválidas, When login, Then 401 y sin sesión.
- Given usuario de otro merchant, Then no ve datos de merchants ajenos.

#### US-E1-02 — Alta Merchant (owner)
**Como** owner, **quiero** crear mi comercio (nombre, país, moneda, timezone), **para** empezar el programa.

**AC:**
- Given datos válidos, When create, Then `Merchant.status=active` y Subscription en `trialing` (14 días) con founding/list según FR-060.
- Given timezone IANA válido elegido por el comercio (ej. `America/Bogota`, `America/Montevideo`), Then se usa para ventanas de topes y “hoy”. No hay timezone por defecto de país.

#### US-E1-03 — Crear / editar Program
**Como** owner, **quiero** definir N, la recompensa y la bienvenida, **para** que el programa sea claro.

**AC:**
- Given programa nuevo sin valores, Then defaults: `stamps_required=10`, `welcome_stamps=2`, `welcome_reason`=“Regalo por unirte a {{negocio}}”, `post_burn_bonus_stamps=0`, topes 2/1.
- Given `stamps_required` ≥ 1 y `reward_label` no vacío, When PATCH/create, Then programa `active`.
- Given `welcome_stamps` fuera de 0–2, Then 400. Given `welcome_stamps>0` y `welcome_reason` vacío, Then 400.
- Pantalla Programa muestra ayuda: “Recomendado 8–10 visitas al premio. Si pones 12, combina con 2 sellos de bienvenida.” Sin opciones de Wallet.
- Given intento de setear `expires_stamps=true` o `stamps_transferable=true`, Then API rechaza o ignora; siempre false.
- Given `staff` (no owner), When PATCH program, Then 403.
- Given pausar programa, When `status=paused`, Then earn/burn rechazados con error claro.

#### US-E1-04 — Caps diarios
**Como** owner, **quiero** límites diarios de earn/burn por cliente, **para** reducir abuso.

**AC:**
- Defaults `max_earns_per_day=2`, `max_burns_per_day=1` (A5).
- Caps editables por owner; visibles en pantalla Programa.
- Se cuentan por membership y día natural en la timezone del merchant; los `adjust` de sistema no cuentan.

### E2 — Person + Membership + invite
**Objetivo:** Invitar cliente por teléfono (y sumar el primer sello en el mismo gesto) y activar membership.

#### US-E2-01 — Invitar + primer sello en mostrador
**Como** staff, **quiero** invitar con teléfono E.164 (+ nombre opcional) y sumar el sello de la visita en el mismo gesto, **para** no hacer esperar al cliente.

**AC:**
- Given teléfono E.164 válido nuevo en el merchant y `earn_now=true`, When invite, Then en una transacción: find-or-create Person, Membership `pending`, evento `earn` (+1, `balance_cache=1`), WA invite encolado.
- Given `earn_now=false`, Then igual pero sin earn.
- Given misma `idempotency_key`, When reintento, Then misma respuesta, sin segundo earn ni segundo WA.
- Given teléfono inválido (no E.164), Then 400 con mensaje claro.
- Given ya existe Membership `(merchant, person)` `active`, Then 409 “ya es cliente” (la UI ofrece ir a +sello); si `pending`, reenvío según A8 (sin earn adicional fuera de topes); si `declined`/opt-out, permitir re-invite → `pending` (G1).
- Given mismo teléfono en otro merchant, Then misma Person, nueva Membership (saldos independientes).

#### US-E2-02 — Confirmar invite (inbound *SÍ*) + sellos de bienvenida
**Como** cliente, **quiero** responder *SÍ* por WhatsApp, **para** activar mi programa.

**AC:**
- Given Membership `pending` (balance 1 por earn_now) y `welcome_stamps=2`, N=10, When *SÍ*, Then `active`, `whatsapp_opt_in=true`, evento `adjust` sistema +2 (`reason_code=welcome_endowment`), balance 3, WA bienvenida “Llevas 3 de 10” con el motivo.

### E3 — Ledger earn / burn / adjust + idempotency
**Objetivo:** Fuente de verdad append-only con anti-abuso.

#### US-E3-01 — Earn (+sello)
**AC:**
- Given Membership `active`, Program active, bajo cap diario, When earn con `idempotency_key`, Then evento `earn`, `balance_cache` += `stamps_per_earn`, `last_activity_at` actualizado, un WA earn (o earn+reward si umbral).
- Given `reward_available` pasa a true, Then mensaje earn+reward.
- **Negativo — doble-click:** misma `idempotency_key` → sin segundo evento; respuesta idempotente.
- **Negativo — invite no active:** `pending` o `declined` → 409/422; sin evento (salvo FR-016).
- **Negativo — cap diario:** ya 2 earns en el día local → rechazo con motivo.
- **Negativo — program paused / merchant paused:** rechazo.

#### US-E3-02 — Burn (canjear)
**AC:**
- Given `balance_cache >= stamps_required` y `reward_available`, When burn con `idempotency_key`, Then evento `burn` delta −N, balances actualizados, WA burn con puente, auditoría.
- Operación en transacción con lock de membership.
- **Negativo — sin saldo / replay / cap burns (1/día) / transferable:** rechazo; sin evento; no existe transferencia.

#### US-E3-03 — Adjust (corrección)
**AC:**
- Given `reason` no vacío y `idempotency_key`, When adjust (owner), Then evento `adjust` `reason_code=manual`, `balance_after` coherente, auditoría.
- Given `staff`, Then 403. Given `reason` vacío, Then 400.
- Balance nunca negativo tras adjust — **default: rechazar balance < 0**.

#### US-E3-04 — Invariante no transferencia / no cash-out
**AC:**
- No API de transfer/P2P/cash-out; tests verifican ausencia de rutas.
- Burn solo reduce saldo in-kind en el mismo membership/comercio.

## 8. NFRs

### 8.1 Security
- Auth obligatoria en todas las mutaciones; autorización por `merchant_id` del staff.
- Passwords hashed (o magic link); HTTPS only.
- Rate limit login (ej. 10/min/IP).
- No exponer teléfonos completos a rol `staff` en listados (enmascarado).
- Secrets de WhatsApp/billing solo en server-side; webhook inbound con firma validada.
- Un comercio nunca puede modificar la Person global ni datos de otro comercio (FR-050).
- KYC ligero merchant: al menos email verificado + nombre comercio.

### 8.2 Privacy
- Datos de Person/Membership solo visibles al merchant dueño de la membership.
- No compartir saldos entre merchants.
- WhatsApp: solo mensajes transaccionales del programa; sin marketing blast en MVP; *BAJA* respetado siempre.
- La invitación identifica al comercio, la finalidad y cómo darse de baja. Revisión legal ligera antes de cobrar en el primer mercado de pago.
- Minimización; retención/borrado = OQ-4.

### 8.3 Idempotency
- `idempotency_key` (UUID) en invite (con `earn_now`), earn, burn, adjust; welcome con key determinista.
- Unique constraint DB `(merchant_id, idempotency_key)` o global.
- Retry seguro desde UI.

### 8.4 Rate limits
- Topes de negocio: `max_earns_per_day` (2), `max_burns_per_day` (1) por membership y día en tz del merchant.
- API: límites anti-abuso (ej. 60 req/min/staff) — builder ajusta.
- Reenvío invite: 1/24h/membership (A8).

### 8.5 i18n / moneda
- Copy producto y WhatsApp en **español**.
- Fechas/números según locale; timezone **por merchant** (obligatoria, sin default de país).
- **Precio mostrado** siempre en la moneda local del comercio (`price_amount` + `currency`); MXN solo como ancla interna, nunca mostrado a un comercio de otra moneda.

### 8.6 Audit
- `StaffAuditEvent` para acciones sensibles (FR-051).
- Ledger inmutable como audit financiero de sellos; eventos de sistema con `actor_staff_user_id=null` y `reason_code`.
- Retención mínima: duración soft launch + margen; política formal post-MVP.

### 8.7 Reliability
- Earn/burn/invite+earn: consistencia fuerte en DB (transacción).
- WhatsApp: eventual; cola de reintentos.
- Objetivo soft launch: “good enough” para 1–N cafés; no SLA público.

### 8.8 Accessibility / UX panel
- Panel ligero, mobile-friendly; targets táctiles grandes para +sello / canjear.

## 10. API contract

Todas las mutaciones: autenticadas, scoped a `merchant_id` del staff, auditadas cuando aplique. Errores: 400 validación, 401 auth, 403 rol, 404, 409 conflicto (idempotency replay distinto payload / phone collision / duplicate membership), 422 regla de negocio (pending invite, cap, saldo).

| Método | Ruta | Body / query | Respuesta (mínimo) | Notas |
|--------|------|--------------|--------------------|-------|
| POST | `/auth/login` | `{ email, password }` | `{ token, staff_user, merchant }` | |
| GET | `/program` | — | Program activo | 404 si no hay |
| PATCH | `/program` | `{ stamps_required?, reward_label?, name?, status?, max_earns_per_day?, max_burns_per_day?, welcome_stamps?, welcome_reason?, post_burn_bonus_stamps? }` | Program | Solo owner; flags expiry/transfer rechazados; `welcome_stamps` 0–2 |
| GET | `/memberships?query=` | `query`, filtros opcionales (`almost_ready` P1) | Lista memberships | Enmascarar phone según rol |
| POST | `/memberships/invite` | `{ phone, name?, earn_now?: bool (default true en UI), idempotency_key }` | `{ membership, person_ref, event? }` | Atómico (§10.1) |
| POST | `/memberships/:id/earn` | `{ idempotency_key }` | `{ event, membership }` | |
| POST | `/memberships/:id/burn` | `{ idempotency_key }` | `{ event, membership }` | |
| POST | `/memberships/:id/adjust` | `{ delta, reason, idempotency_key }` | `{ event, membership }` | Solo owner |
| POST | `/memberships/:id/phone` | `{ new_phone, reason }` | Membership (nuevo `person_id`) | staff_local; reasigna Membership; 409 si colisión |
| POST | `/memberships/:id/confirm-in-person` | `{ reason? }` | Membership active | Fallback; sin welcome; auditar |
| POST | `/memberships/:id/resend-invite` | — | ok | Rate limit A8 |
| GET | `/analytics/summary?from&to` | fechas ISO opcionales | ver abajo | |

### 10.1 Flujo atómico invitar + primer sello
1. Staff envía `POST /memberships/invite { phone, name?, earn_now: true, idempotency_key }`.
2. Transacción: find-or-create Person → create Membership (`pending`, `whatsapp_opt_in=false` hasta *SÍ*) → si `earn_now`, `StampLedgerEvent{type=earn, delta=+stamps_per_earn, actor=staff, idempotency_key}` (cuenta para topes y KPIs) → `StaffAuditEvent(action=invite_earn)` → encola WA invite (plantilla aprobada).
3. Replay con la misma key → misma respuesta; ningún evento ni WA adicional. Misma key con payload distinto → 409.
4. Cliente responde *SÍ* (webhook) → `active`, `whatsapp_opt_in=true` → si `welcome_stamps>0`: `StampLedgerEvent{type=adjust, delta=+welcome_stamps, actor_staff_user_id=null, reason_code=welcome_endowment, reason=welcome_reason, idempotency_key="welcome:{membership_id}"}` → WA bienvenida con `actual / N`.
5. Si el cliente no confirma: la Membership queda `pending` con su earn (visita real, no se anula); no recibe más WA que los reenvíos A8; los siguientes earns requieren `active`.
6. Auditoría: earn en ledger con actor staff; welcome en ledger con actor sistema + `reason_code`; invite/confirm en `StaffAuditEvent`.

`almost_ready_count` es P1 (E-PSY-5). `suggestions` vacío si no hay señal. Códigos: `low_redemption`, `inactive_customers`, `pending_invites`.

### Webhook inbound WhatsApp (implementación)
- Ruta interna a elección del builder, ej. `POST /webhooks/whatsapp`.
- Valida firma del proveedor; from-phone → Person.
- *SÍ* → Membership pending → active (+ welcome). *BAJA*/STOP → `whatsapp_opt_in=false`. Cualquier otro texto → ignorar.

### Definiciones operativas (para no adivinar)
Regla general: excluir eventos `reason_code=welcome_endowment` (y `post_burn_bridge`) de todos los KPIs.

| KPI | Definición implementable |
|-----|--------------------------|
| Activos 30d | Distinct memberships con ≥1 `earn` en últimos 30d (tz merchant) |
| Earns/Burns 7d | Count eventos `earn`/`burn` en últimos 7d |
| Tasa canje 30d | **Abierto, default propuesto (OQ-5b):** burns del periodo / memberships que tuvieron `reward_available=true` en algún momento del periodo (o lo arrastraban al inicio). Sellos solo de bienvenida no cuentan para alcanzar N. Denominador 0 → `null` y sin sugerencia |
| Listos | `reward_available = true` y `invite_status=active` |
| Casi listos (P1) | `invite_status=active`, `balance_cache >= N−2` y `< N` |

Ver §2.3 (desde ledger, sin pantalla nueva).

## 12. WhatsApp copy reference (ES) — copy deck único (PMAT §4, anti-reactancia)

**Fuente única de verdad** (el Brief remite aquí). Todas son plantillas utility a aprobar por Meta.

**Invitación:**  
Hola{{nombre}}. En {{negocio}} sumas 1 sello por visita. Con {{N}} sellos: {{recompensa}}. ¿Te apuntas? Responde *SÍ*. Si no quieres recibir mensajes, responde *BAJA*.

**Bienvenida (con endowment):**  
¡Listo! Ya estás en {{negocio}}. {{#if welcome}}{{welcome_reason}}: te regalamos {{welcome}} sello(s). {{/if}}Llevas *{{actual}} de {{N}}*. Te avisamos aquí cuando sumes o canjees.  
*(Ej.: “Regalo por unirte a Café Luna: te regalamos 2 sellos. Llevas 3 de 10.” — si `welcome_stamps=0`, se omite el bloque del regalo.)*

**Earn:**  
+1 sello en {{negocio}}. Llevas *{{actual}} de {{N}}*; te faltan *{{faltan}}* para {{recompensa}}.  
*Hitos (mismo mensaje, nunca un segundo WA):* faltan 2 → prefijo “¡Casi! ”; faltan 1 → prefijo “¡Uno más! ”.

**Earn + recompensa:**  
+1 sello. ¡Ya puedes canjear {{recompensa}} en {{negocio}}! Pídeselo al equipo. Llevas *{{actual}} / {{N}}*.

**Burn (puente post-canje):**  
Canjeado: {{recompensa}} en {{negocio}}. Nuevo ciclo: *{{actual}} / {{N}}*. En tu próxima visita seguimos sumando. ¡Gracias!

**Notas:**
- Tono anti-reactancia: sin urgencia falsa, countdowns, “última oportunidad” ni “perderás tus sellos” (no hay caducidad).
- Inbound técnico solo *SÍ* y *BAJA*; sin conversación.
- Si `stamps_per_earn` ≠ 1, adaptar a “+{{delta}} sello(s)” (default 1).
- `{{nombre}}`: si falta, “Hola.” sin coma rota.

## 13. Launch plan (soft launch)

### Criterios de done (checklist brief §12)
- [ ] Comercio puede crear programa (N + reward; defaults psicología y topes)

- [ ] Home con KPIs mínimos (§8.4) y listas pendientes / inactivos / listos para canjear

5. Cobro manual founding/list en moneda local según L7/A4.
6. Observar 1–2 semanas: fricción taps, confirmación *SÍ*, *BAJA*, fallos WA, métricas §2.3.

## Apéndice B — Casos negativos obligatorios (regresión)

1. Doble-click earn misma idempotency_key → 1 evento.
2. Burn sin saldo → rechazo.
3. Earn con invite `pending`/`declined` → rechazo (salvo invitar+sumar atómico).
4. Earn con program `paused` → rechazo.
5. Transferencia / P2P / cash-out → no existe.
6. `stamps_transferable=true` → imposible.
7. Phone change a número cuya Person ya es cliente en este comercio → 409; Person global nunca editada.
8. Adjust sin reason o por staff → rechazo.
9. Superar `max_earns_per_day` (2) → rechazo; welcome no cuenta.
10. Replay burn misma key → sin segundo canje.
11. Replay invite+earn misma key → sin segundo earn ni WA.
12. *SÍ* repetido / re-invite → un solo welcome por membership.
13. Confirmación en persona → sin welcome.
14. *BAJA* → ningún outbound posterior.
15. Comercio creado tras `founding_window_ends_at` o con 50 slots reservados → `plan=list`.
